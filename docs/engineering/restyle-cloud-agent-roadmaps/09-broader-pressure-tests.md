The security proposal concerns the foundation for all generated code: Restyle supplies and enforces permitted effects, while the model implements the requested experience using those effects. ### What remains a design responsibility

The model currently proposes the service agreement, including operation audience and result shapes, before implementation. The host validates and freezes that contract. Execution is independent of generated tests, but a structurally valid contract can still misinterpret the creator's intent. Passing its examples does not prove that the chosen permissions or public output are appropriate.

A synthetic characterization confirms the distinction without executing or publishing generated source: a public caller cannot invoke the creator operation; the public invocation contains the agreed service state; a fixed result enum rejects an unexpected private marker; a separate valid contract allowing arbitrary strings accepts that same marker as a result. Changing the agreement in this local comparison is not a caller bypass or an observed production leak. It establishes that the current boundary enforces the saved contract, not automatic information-flow protection inside arbitrary code.

The smallest design direction is to retain the existing host adapters and make the responsibility explicit:

1. Describe required capabilities from the creator's actual PVO request. Use the existing built-in operation where it already supplies the requested behavior.
2. Keep ownership, credential access, allowed destinations and live-effect approval in trusted platform policy. Model output and successful tests cannot grant these permissions.
3. Give custom computation only data appropriate to its permitted outputs. Any stronger promise about private-data processing needs an explicit access/output policy outside the generated implementation; unrestricted shared state plus arbitrary public strings cannot provide that promise by itself. Choose a narrow change only after demonstrating a required existing workflow, rather than introducing a generic identity or permission system.
4. Evaluate product correctness and platform enforcement separately. Actual PVO requests exercise understanding, editing, compilation, interaction and recovery. Fixed malicious source/requests exercise the host independently of whether the current model happens to generate safe code. Unsupported requests exercise honest capability handling.

The inbox's existing [abuse key](../../../server/replies/source.js) is a per-box, per-day HMAC of the supplied Cloudflare IP header. It is not proof of the same device or person, and grants no viewer read/update permission. This review adds no tracking or viewer-identity mechanism.
