# Orb assistant

The editor's existing orb accepts questions and editing requests for the whole project. Selection supplies context but is not required. It can edit text, clips, scenes, audio and components, inspect sampled footage, transcribe a bounded audio range, and open the existing export flow. It also supports [public web research and font import](web-search.md), with saved fonts shared across projects in this browser. A single composer accepts typed requests, microphone input with explicit **Send**, or hold-to-speak input from the orb; there are no mode tabs. Requested edits apply immediately after validation on both phone and desktop, as one undoable project edit. Questions open an answer card with **Done** and follow-up actions.

The orb keeps a visible Restyle thread for the current editing session. Tapping the orb opens the composer; after an exchange, a count button beside the orb opens the thread with its requests, working status and results. Its composer sends through the same native assistant command. On phones the thread replaces the timeline panel and can be resized; on desktop it opens above the orb. Closing the thread retains its exchanges and draft. Account/project changes and reloads clear the thread; scope guards reject delayed answers and errors even after switching away and back. The thread is excluded from project saves, exports and undo history, and its length and response text are bounded. A row's **Show** action returns to the selection that supplied context for that request when it still exists.

Cloud authoring-task locators have a separate [local project association](restyle-cloud-agent-roadmaps/1b-saved-tasks.md#1b02--link-the-notebook-to-the-local-draft). Only owner/project/task IDs are added to local checkpoints; the ordinary conversation remains session-only. Server task storage and background authoring are later work.

The assistant is available outside Try mode and timeline pickers, including the desktop component inspector and expanded Advanced IDE. Normal phone component sheets hide it. Selecting a component adds a violet ring. Opening the assistant pauses playback without moving the playhead or resizing the workspace. Closing it or completing an edit restores the previous playback state in the same editing scene unless the request deliberately changes playback.

Expanding Advanced places the existing assistant inside the black source surface using a portal; it does not mount a second session. Its floating controls stay within that surface and participate in the desktop focus scope. Header, navigation and source controls pause individually while the assistant is active, leaving the nested assistant interactive. The source surface reaches the panel bottom, and its scroll padding lets the last code line move above the orb and phone safe area. Collapse restores normal placement; finish the active assistant interaction first. The source editor stays mounted across expansion and collapse.

On phones the toolbar remains 100 px tall, plus the bottom safe inset. Its normal buttons unmount while the assistant borrows that space; nothing is dimmed. The 58 px idle orb sits at the right edge, overlapping the toolbar by 22 px. An awake orb uses the accent colour and full-size mark, lifts 8 px and breathes over 1.6 seconds. Typing moves it left; working keeps it right. Holding from typing listens at the left, while holding from idle listens at the right. The context row identifies the selected component or the whole edit and offers a voice hint. An answer centres the orb and raises it 14 px, with follow-up chips and an answer card. Desktop uses its compact inline composer. Both layouts apply edits with the same commands and Undo behavior. System and app reduced-motion settings remove decorative animation.

## Ownership and application

| Area | Responsibility |
| --- | --- |
| `editor/src/features/assistant/` | Prop-driven views, placement, focus and session orchestration. `useAssistantSession` coordinates requests, application, answers and project-staleness checks. |
| `features/assistant/voice/` | Microphone start/Send/Cancel, orb tap/hold events and one cancellable microphone recording/transcription session. |
| `packages/pvo-assistant/` | Common PVO source types and compiled component policy. `native/` owns strict native operations, observations and project context. |
| `editor/src/domain/assistant/` | Answer data, bounded context, isolated batch preparation, completion summaries and failure classification. No React or store dependencies. |
| `editor/src/infrastructure/assistant/` | Same-origin HTTP transport, bounded planning workflow, microphone capture/transcription and browser-owned frame/audio inspection. |
| `server/assistant/native/` | Inference, request limits, observation validation, transcription and provider availability. |
| `editor/src/state/assistant/assistantStore.ts` | Session-only `idle`, `typing`, `listening`, `working` and answer-reading `review` state. |
| `editor/src/state/assistant/threadStore.ts` and `threadCommands.ts` | Session-only visible exchanges and guarded row actions; planner history remains in `assistantStore`. |
| `editor/src/state/assistant/nativeCommands.ts` | Commits a validated project batch atomically through normal history. |
| `editor/src/state/assistant/applyChanges.ts` | Coordinates the commit and requested playback/export effects; playback uses shared editor commands. |
| `editor/src/state/assistant/nativeAppliedNotification.ts` | Owns the temporary Undo receipt and verifies it still identifies the current edit. |

The orb sends internal `plan` requests automatically. The model chooses whether the next step needs an answer, observations or operations. The server rejects a turn that combines media requests with edits. The browser runs at most six rounds against a private working copy. After each operation batch passes local validation, the next turn receives that candidate's metadata, actual generated IDs and available component source. Later steps can inspect or refine the candidate without changing the open project or repeating already prepared work. A `component.style` operation patches only its supplied declarations into the current Style; broad visual requests should vary supported spacing, type, shape and shadow as well as colour. This checks project data and compiled source; it does not verify the rendered pixels of interactive components.

One local preparation failure can return its diagnostic to the model for correction against the unchanged candidate. An exact repeated edit receives one correction turn without executing the duplicate; a second repeat stops the task. A repeated successful inspection can reuse the same result once without another media decode or inference call. Policy failures stop immediately, and a second preparation failure ends the task. A terminal response with no operations or observations ends preparation. A genuine blocker also carries `blocked: true`; the browser discards every prepared change and shows its focused question or limitation. Otherwise the browser validates the accumulated batch and the original project fingerprint before applying it once through normal history. Stop, stale project state or failure also discards the private candidate. There is no staged preview, Before comparison or Keep step. The six-round lifecycle and bounded media requests limit an individual task. Each provider-backed HTTP request also reserves capacity from the shared application budget before inference begins.

An applied project edit shows one typed `assistantApplied` notice for 2.4 seconds, pausing its dismissal while hovered or focused. Copy comes from validated operation kinds, not model-generated completion claims. Its **Undo** action reverses only that exact edit: a later manual edit, different project or changed history invalidates the receipt. The ordinary editor Undo remains available after the notice disappears. A thread row offers **Undo** or **Redo** while its exact project and history state is still current; a later edit disables that row action. The row follows ordinary editor Undo and Redo. This assistant-specific feedback is an approved exception to quiet routine edits in the [notification policy](notification-policy.md). Playback-only requests and opening export do not create artificial project history or an Undo notice. Export download and publication still use the existing export workflow.

Questions alone produce an answer card without a project edit. A request combining edits with a substantive question applies the complete batch and shows the requested information in the same existing answer card; a routine edit confirmation does not open it. **Done** closes it, tapping the request returns to typing, and follow-up actions send another request against the current project. On mobile, tapping outside the composer closes typing or listening and returns to the main tools. Escape also closes typing or listening and cancels working requests. Tapping the working orb stops the request and restores typing. Enter sends from the input. Unsupported requests retain their wording and use the approved single top notification.

Only one request runs at a time. The existing working bubble or desktop pill announces the actual stage: reading the project, inspecting footage, transcribing audio or validating edits. The working orb displays **Stop** and cancels back to the retained request, ready to edit or resend. Completion, cancellation and failure clear the working state. Usage-limit failures use the top notification; they do not leave the orb processing.

The Advanced switch restricts **AI logic only**, not wording or appearance. With Advanced off, new behavior must use Continue, Jump to a point or Go to a scene; existing advanced behavior stays unchanged. Custom PVO colours, typography, corners and other compiler-supported visual edits remain available. Batch preparation reads the current Advanced preference, compiles exact sources and enforces this boundary. The commit checks the preference again so a setting change during inference cannot apply disallowed logic. A blocked attempt preserves the request and project and shows only “Enable Advanced for this logic change.” Enabling Advanced retains the request-domain and capability safeguards; it does not grant network access.

Drafts, transcripts, sampled images and answers remain outside project persistence and undo history. Prepared batches exist only within the request workflow. The session retains up to 12 conversation entries and eight textual evidence records, including timestamped vision descriptions, transcripts or unavailable-inspection results. Conversation and evidence each retain at most 16 KiB, with up to 4 KiB per entry. Before each turn the workflow reserves the current project, prompt and observations inside the server's 48 KiB textual request boundary, then fits recent history into the remaining space. Frame image bytes have their own transport limit and are not retained. Evidence uses a fingerprint appropriate to what was inspected. Transcripts survive text, component and appearance edits, but changes to source audio, clip order, timing, speed, gain or mute invalidate them. Frame descriptions require the exact project snapshot. Unavailable inspections are also tied to that snapshot. The final candidate is checked before evidence enters follow-up memory. Changing projects or resetting the assistant clears session memory.

A project fingerprint guards requests, media inspection, preparation and the final commit. Manual changes make the request stale instead of being overwritten. Project changes, unavailable editor modes, Stop and unmounting cancel pending work; late responses cannot apply edits. IDs identify specific objects rather than depending on whichever component is selected when a response arrives.

## Native service and model access

The orb uses same-origin **`POST /api/assistant/turn`** with no login dependency. **`GET /api/assistant/status`** reports configured availability and the ChatGPT access gate; editing fails closed when either the selected model or the application budget binding is unavailable. **`POST /api/assistant/transcribe`** transcribes browser-extracted audio. Every provider-backed POST reserves one application-budget request after validation and before inference. All routes return `Cache-Control: no-store`; mutation-style requests require the configured exact origin and reject cross-site requests. Provider credentials stay in Workers bindings, never in the browser. Before each new Orb task, the browser reads status and requires the editing capability; an unavailable, failed or malformed status preserves the draft and prevents a provider turn. There is no preset response fallback or artificial delay.

`server/assistant/native/` selects one inference provider explicitly. The beta deployment configuration sets `ASSISTANT_PROVIDER=runpod` for text, vision and transcription with no automatic cross-provider fallback. It requires a server-side `RUNPOD_API_KEY` secret; the Codex Runpod connection does not supply credentials to the deployed website. The Cloudflare adapter remains available for explicitly configured development environments.

The Cloudflare configuration uses three Workers AI models:

| Responsibility | Provider model |
| --- | --- |
| Planning and typed operations | [Llama 3.3 70B](https://developers.cloudflare.com/workers-ai/models/llama-3.3-70b-instruct-fp8-fast/) |
| Sampled-frame understanding | [Moondream 3.1](https://developers.cloudflare.com/workers-ai/models/moondream3.1-9B-A2B/) |
| Speech transcription | [Whisper Large v3 Turbo](https://developers.cloudflare.com/workers-ai/models/whisper-large-v3-turbo/) |

Runpod configuration belongs to the server environment:

```env
ASSISTANT_PROVIDER=runpod
RUNPOD_API_KEY=<server secret>
RUNPOD_TRANSCRIPTION_ENDPOINT=<WhisperX endpoint ID>
```

The beta configuration selects the existing `speaker-studio-whisperx` endpoint (`5uqruzvtb96kph`) for media transcription. Text and vision use the managed Runpod Public Endpoint described below; they do not create an account-owned GPU worker. Configure the API key as a Worker secret before deploying and verify real text, image and transcription requests. A missing secret fails closed. Microphone dictation uses the same Runpod transcription endpoint after explicit Send or hold release; Safari needs microphone access, with no Siri or browser speech-recognition dependency.

Text and sampled-frame understanding use [Kimi K2.6 through Runpod's hosted endpoint](https://docs.runpod.io/public-endpoints/models/moonshot-kimi) with non-thinking mode enabled through its OpenAI-compatible API. The server still performs typed operation validation and completion review. Transcription uses a configured WhisperX worker implementing `audio_file`, `align_output`, `diarization` and `batch_size`, returning timestamped `segments`. Fully aligned words become native transcript segments with their measured start/end times, while the full sentence text is preserved. Incomplete alignments retain the original sentence segment; malformed supplied timestamps are rejected. When word detail exceeds the 300-segment response boundary, the complete original segment coverage is retained instead of truncating the end. The verified worker contract is [whisperx-worker_v2 at cd51be6de](https://github.com/kodxana/whisperx-worker_v2/blob/cd51be6deedf5a36415ea1cc35e1b91314679819/src/rp_handler.py). Missing transcription configuration disables that capability, rather than sending audio to Cloudflare. Credentials stay server-side. Responses are bounded and parsed; redirects and provider error bodies are rejected. Each transcription request owns one queued job and cancels it on Stop, deadline or failure. No pods or endpoints are created by an editor request.

A Codex Runpod MCP connection authorizes tool calls in Codex; it is not a credential available to the website. A temporary local test relay can exercise actual Runpod inference through that connection, but it only works while Codex is servicing it and is not a deployed authentication solution.

These are hosted inference services with model-specific licenses, not on-device inference. Moondream uses a [source-available license](https://moondream.ai/licenses/model/1.0), which permits its use within a domain-specific application. The selected vision adapter sends actual frame images to its vision model, then sends the returned descriptions and exact timestamps to the text model. It does not ask the text-only planner to interpret image URLs or base64 text.

The planner receives operation and observation shapes derived from the canonical contract: exact keys, required fields, types and enums, filtered by the session's available capabilities. Separate branches permit edits, observations, a terminal answer or an explicit blocker. Ask mode has no editing branch. Generation omits inner string/array bounds and numeric ranges to limit provider grammar complexity; the full shared parser still enforces all of them, followed by compilation and policy validation. Provider schema guidance does not establish correctness.

When the initial result has no operations or observations, the server performs one nonrecursive model completion review against the latest request, candidate project, prepared changes and existing evidence. That review can retain a useful answer, request missing evidence, supply missing operations or confirm an explicit blocker. A premature blocker can become a further inspection step when available evidence can resolve it. It reuses vision descriptions rather than running frame inference again. The latest request is repeated as the active task after historical context and in completion/repair messages. Historical requests describe context; they do not authorize repeating old edits. The instructions require the assistant to inspect available source and relevant footage before asking for observable facts, choose routine creative details itself, and ground factual answers in evidence. Already-transcribed ranges can be narrowed when the existing speech segments are too coarse to answer a timing question; precise or silent evidence does not trigger redundant transcription.

The initial response and completion review share one schema repair attempt, so a turn makes at most three text-model calls. Provider failures propagate without a model retry. Cloudflare text inference has a 25-second deadline and each frame inference 20 seconds. Runpod allows 60 seconds for each text or frame inference. Independent frames run with bounded concurrency of three and preserve their original timestamp order; failure cancels sibling calls. The entire turn, including frame inspection, completion review and repair, has one 90-second deadline. The browser transport allows 95 seconds including response decoding. Cloudflare transcription has a 45-second server deadline. Runpod transcription allows 90 seconds for queuing and inference, with a 95-second browser deadline and a short bounded cancellation attempt. A model completion review is a semantic check, not proof of factual correctness or rendered appearance.

Validation diagnostics identify the decoding/schema/policy stage, repair or review phase, canonical field path, allowlisted tool kinds and bounded counts. Unknown property names and exception text are omitted. Prompts, component source, field values and model replies never enter these logs; public errors retain their fixed notification copy. Each request records at most twelve events. A provider finish reason is recorded only when the adapter supplies one; absence is reported as unknown.

The application budget accepts at most 60 provider-backed requests per UTC day across the service, 20 per client per day and twelve per client per minute. The minute allowance accommodates one task’s maximum six model turns and six metered observations. A client address is hashed together with the UTC date before reaching the Durable Object; prompts, project source, media and raw addresses are never stored there. Each valid turn, transcription, alignment or tracking POST reserves once before provider work begins, even when one turn uses bounded completion review, repair or sampled-frame calls internally. Per-request media sizes, deadlines, validation and one repair attempt also bound each operation. [Cloudflare's account allowance](https://developers.cloudflare.com/workers-ai/platform/pricing/) or Runpod's usage billing and limits remain independent; a provider rejection is reported through the existing notification surface. A confirmed exhausted provider allowance has its own fixed notification and stops the task immediately, including when it occurs during transcription; it is not presented as temporary model congestion.

### ChatGPT plan access

ChatGPT identity sign-in and permission to use a ChatGPT plan are separate capabilities. The currently documented [ChatGPT plan integration](https://developers.openai.com/siwc/token-sharing-open-source) is for open-source, locally hosted clients. Remotely hosted apps must request access through OpenAI's linked interest form. PVO's hosted integration is not configured: status returns `chatgpt.available: false` with `reason: "hosted_access_required"`. There is no pretend sign-in, copied Codex credential, undocumented inference endpoint or API-key billing presented as ChatGPT plan usage. Hosted approval and an applicable integration contract are required before adding that provider; anonymous hosted-model use remains available.

### Native wire contract

`/api/assistant/turn` accepts JSON `{mode,prompt,history,project,observations}` and returns `{message,operations,observations,blocked?,answer?,evidence?}`. The canonical types and parser are [`packages/pvo-assistant/native/`](../../packages/pvo-assistant/native/index.d.ts). `ask` cannot return operations; `plan` prepares validated operations in the browser's private working copy; `edit` permits that workflow to commit its accumulated batch after a terminal response. The server never mutates the editor. These are internal execution controls, not separate UI modes. The orb uses `plan` throughout the loop, then applies the accumulated batch through the shared commit command after final validation. An answer needs no operations. `blocked` is optional positive metadata: only `true` is accepted, and it requires empty operations and observations. It means the task cannot finish without unavailable information, an unsupported capability or a necessary user choice; any prepared candidate must be discarded. Completed tasks, normal answers and further steps omit the flag. Optional `answer` carries a requested substantive textual answer accompanying completed edits, such as spoken words or an analysis. It must be nonblank, at most 8,000 characters, and occur only on an unblocked terminal result with no operations or observations. The completion reviewer preserves or supplies this requested answer; ordinary edit confirmations omit it, and questions without edits use `message`. Each response contains at most 24 operations or four observation requests; it cannot contain both.

Project context describes scenes, clips, text, audio, components, selection and timing without media URLs, file paths or request payloads. Interactive components include their current `responsePolicy`, so the assistant can inspect whether they wait for an answer and when that answer takes effect. Request-bearing components omit their full source; safe content and appearance edits reconstruct the real source locally and preserve request effects. The server limits textual context to 48 KiB, all frame images together to 2 MiB and the complete JSON body to 3 MiB. The prompt is at most 4,000 characters. Unknown fields and operations are rejected, not ignored or partially applied.

`component.add` accepts an optional `responsePolicy`, and `component.update.changes.responsePolicy` changes the same authored setting. Both fields use `{dispatch:"interaction"|"layer_end",unanswered:"continue"|"pause"}`. Dispatch controls whether a response takes effect when clicked or when the layer ends. Unanswered playback either continues or waits at `at + duration`; it does not pause when the component first appears. A quiz that must wait before a spoken reveal therefore needs its layer end before the observed reveal time, together with `unanswered:"pause"`. A Continue response resumes playback. This behavior is exercised in Try and the exported viewer; ordinary Edit playback remains a timeline inspection tool. These are existing component settings exposed to the assistant, with no new UI or playback engine.

Frame requests contain `{kind:"frames",sceneId,start,end,count}` with at most six frames across one turn. Ranges are scene timeline seconds. The browser samples interval midpoints and maps each through the clip's source trim and speed. Temporary decoders render authored fit, zoom, mirror and text into bounded JPEG images. Every sample carries its scene time, source time and clip ID. Captures exclude sandboxed interactive components and explicitly report that coverage limit. Sampled frames do not establish what happened between samples. The server also returns optional textual `evidence` derived from those actual vision results: at most six timestamped descriptions, 2,000 characters each and 8,000 combined. The text planner cannot supply this field. The browser retains it as untrusted observation data across later rounds, so a later transcript can be combined with earlier visual evidence without sending the images through vision again.

Transcript requests contain `{kind:"transcript",sceneId,start,end}` for at most 60 seconds. The browser mixes audible clip/audio-layer ranges into mono 16 kHz, 16-bit PCM WAV and posts the bytes with `Content-Type: audio/wav`. The server validates the RIFF chunks, format, actual sample duration and byte limit before inference; the optional `X-Audio-Duration` must agree. The response is `{text,segments:[{start,end,text}]}` in submitted-audio seconds. The browser maps these to scene time. Missing provider timings remain an empty list, not invented word timings. Temporary videos, audio contexts, decoded buffers, listeners and requests are released or cancelled by their owning adapter.

### Optional local word timing

`word_timing` aligns a supplied English transcript to a single audible source using the [pinned local MFA service](../../scripts/dev/mfa/README.md). This is an additional observation tool, not a new interface or a replacement for transcription. The planner uses it when a coarse transcript does not identify the requested spoken boundary. The browser extracts original-speed PCM and maps measured words through clip trims, scene placement and playback speed. Overlapping sources, unsupported languages and stale source references are rejected; failed alignment cannot authorize a partial edit.

The local Worker requires `ASSISTANT_LOCAL_DEVELOPMENT=true`, `MFA_ALIGNMENT_URL=http://127.0.0.1:5198/align` and a private `MFA_ALIGNMENT_TOKEN` matching the service. Keep the token in ignored `.dev.vars`, never client code. `/api/assistant/status` exposes only `capabilities.wordTiming`. Current clients also send `X-Assistant-Word-Timing: 1` on planning requests; an already-open older beta is not offered a tool it cannot execute. This loopback service is local development infrastructure; a hosted deployment needs its own service adapter.

Alignment returns estimates with model/runtime provenance and `transcriptVerified:false`. Successful alignment does not prove the transcript is correct: omitted spoken words can still produce a result. The tested MFA 3.4.2 runtime requires the reproducible refinement correction described in the service README; stock `--fine_tune` silently skipped refinement on the test fixture. A 4-second clip took about 23 seconds in the warm CPU CLI, including setup. Millisecond output resolution does not establish millisecond accuracy. Check the boundary in playback, and inspect baked-in captions separately when the task depends on hiding an answer.

### Keyframes and object tracking

The orb shares the manual [layer animation](layer-animation.md) commands. `animation.set`,
`animation.remove` and `animation.clear` author editable curves on video, text, components,
extracted audio and music. Ordinary fades and slides need no tracking model.

When a request depends on an object's movement, `object_tracking` observes a bounded video
range with SAM 3.1, using a description or a normalized point on the first frame. The browser
captures the actual video canvas, including crop, mirror and existing video animation but
excluding overlay text and components. `animation.follow` converts the returned measurements
into editable position keys for text/components, or camera-follow keys on that same source
video. The assistant cannot invent tracking coordinates: the observation ID must match real
measurements registered during the task, and source edits invalidate it before commit.

Manual **Track object** controls use the same capture, service and conversion rules. Matching
multiple objects requests a point instead of selecting an arbitrary identity. Insufficient
tracking fails without applying; measured loss hides an attached overlay and holds camera
position. Tracking observes at 15 fps, so it does not promise exact motion between samples.
It applies as one edit with Undo after data validation, not after an independent visual-quality
judgment. See the animation guide for range, existing-curve and visibility constraints.

The authenticated [SAM service](../../scripts/dev/sam31/README.md) is configured through
server-only `SAM_TRACKING_URL` and `SAM_TRACKING_TOKEN`. It is independent of the text/vision
provider and does not require a Runpod account key in the browser. Status reports
`capabilities.objectTracking`; clients announce `X-Assistant-Animation: 1` and
`X-Assistant-Object-Tracking: 1` so an already-open old beta is not given unsupported operations.
The browser request allows 230 seconds including capture, and the Worker allows 180 seconds
for the provider. Stop cancels the request and prevents a late edit; the current remote
development adapter may finish its bounded in-flight GPU computation after disconnection.

### Local development

Vite and the static `npm run dev` server do not provide inference. Run the Worker with an `AI` binding configured as `remote: true` and the built application as `ASSETS`. Wrangler authentication needs Workers AI access. Local development sends real inference calls to Cloudflare and uses that account's allowance. Workers Free rejects inference after the daily free allocation; Workers Paid can charge for usage beyond it. The application does not change the account's plan or billing settings.

Production requires an exact HTTPS `PUBLIC_ORIGIN`. A local HTTP Worker may opt in with `ASSISTANT_LOCAL_DEVELOPMENT: "true"`; `PUBLIC_ORIGIN` must then be the exact request origin at `127.0.0.1`, `localhost` or `[::1]`, including its port. Cross-origin or cross-site requests remain rejected. This flag applies only to assistant routes and does not enable HTTP creator authentication or publishing.

A beta Worker replacing a static server must keep the same origin to preserve browser storage and editing sessions. Copy built hashed assets before HTML and the service worker, preserve prior assets, and copy `editor/release.json` last. The Worker's release channel is not a file watcher: announce that revision through the authenticated `/api/releases/announce` route after verifying the served assets. Store its announcement secret in an ignored local `.dev.vars` file and never send it to the editor. See [release setup](cloudflare-publishing.md).

HTTP 400, 413, 429, 503 and 504 map respectively to invalid input, input size, provider usage limit, unavailable service and timeout notifications from the approved catalogue. HTTP 422 carries a fixed classification: `model_output_invalid`, `model_output_truncated` or `edit_validation_failed`. These produce distinct short failure notifications and safe diagnostic detail, preserving the request and applying no partial edit. An unclassified 422 is an invalid-response failure, never proof that the user requested an unsupported feature. Actual capability limits remain reviewed `blocked` answers explaining the limit; they do not produce a duplicate failure toast. A usage-limit response means that request was rejected; it does not indicate that the assistant is still working. Provider error bodies are never shown.

## Component validation boundary

The server and browser both validate the envelope, compile the exact proposed source and apply shared component policy before application. Invalid source is rejected rather than repaired by removing declarations in the browser. The component root must match the selected type; Restyle Choice proposals must retain exactly two options. PVO's restricted grammar remains authoritative: assistant output cannot introduce unrestricted HTML, CSS or JavaScript.

Compiler-valid actions are also checked against the current project. Scene routes must name nonempty scenes, and time jumps must stay within the selected scene's duration, including request success/error outcomes. These checks run during preparation; the final commit rechecks the prepared effects and current editing preference. Preview rendering and host actions retain the existing sandbox and request-domain policy; the assistant model service is not added to component request permissions.

New assistant actions are limited to continue, jump to time and go to scene. Existing request actions must remain unchanged on the same event and target, including form field names and types used by request templates; new, changed or removed request effects are rejected. Response-policy edits use the existing interactive-component contract: display-only Notes cannot carry a policy, and a Message without a button cannot pause for an answer. Final batch validation rechecks these requirements after all operations. The compiler validates every Style property, selector and value. Native content and style operations compile the full reconstructed source before the batch can be applied.

## Voice input

Tap the composer's microphone button to begin. The app checks that server transcription is available before requesting microphone access. **Starting microphone…** remains visible while checking availability and waiting for permission, for up to 30 seconds; a permission dialog taking window focus does not cancel tapped startup. **Listening** appears only after `MediaRecorder` confirms recording has started. Audio stays in memory on this device until the user taps **Send**, which accepts a one-word request. **Cancel** stops startup; its action stays Cancel if recording starts between pressing and releasing the button.

A tap on the orb shorter than 320 ms opens typing or focuses the current input. Holding for at least 320 ms starts recording; release authorizes transcription and submission. This gesture requires at least two transcribed words, with the approved brief hold warning for shorter input. Releasing before microphone startup cancels and prevents permission completion from starting a later recording. Recording stops after 60 seconds and remains ready for explicit Send/release; reaching that limit never uploads automatically. Recording has no live word preview. **Transcribing…** appears after Send/release, with a Cancel button while the recording is converted and transcribed.

The browser selects its supported `MediaRecorder` container. `OfflineAudioContext` converts the recording to mono 16 kHz PCM WAV, bounded to 60 seconds; it needs no playback context or user-activation-dependent resume. Silent audio is discarded. The existing same-origin `/api/assistant/transcribe` route supplies the transcript, with a 95-second client deadline, validated response and the existing quota/error classifications. The beta uses Runpod WhisperX for both this route and footage transcription. Browser `SpeechRecognition`, `webkitSpeechRecognition` and Siri are not used. A secure context, a working microphone, browser recording/decoding support and server transcription availability are required. Typing remains available if voice input is unavailable.

Escape, page hiding, closing the assistant, project changes and unmounting discard either voice mode; loss of the held pointer also cancels hold input. Cancellation stops every microphone track, removes recorder listeners and timers, aborts any upload, and ignores late permission/transcription results. Recording bytes are not persisted. Failures preserve the typed draft and return to typing where applicable. Detailed failures remain in assistant diagnostic state, with one concise notification.

## Harness diagnosis and regression checks

Each request emits bounded local `[native-assistant]` trace events for model calls, observations, preparation and application. Events contain stage, status, tool names, elapsed time and safe failure reasons, never prompt text, source, URLs, images or transcripts. Use the failing trace to identify the stage before changing prompts. This follows the trace-first evaluation approach in the [OpenAI agent evaluation guide](https://developers.openai.com/api/docs/guides/agent-evals) and the model/tool/result lifecycle described in [running agents](https://developers.openai.com/api/docs/guides/agents/running-agents).

`scripts/checks/editor/assistant-quiz-followup.mjs` verifies an initial quiz followed by spoiler removal, question changes and timeline adjustments, using real compilation and a single atomic Undo. `assistant-media.mjs` checks actual captured pixels, extracted audio, timeline/source mapping and cleanup. Provider adapter tests cover response validation and cancellation. Deterministic model fixtures prove harness behavior; they do not establish live model quality. Live provider results must be reported separately.
