# Export quality investigation

The editor currently flattens each scene into a canvas, captures it in real time at 30 fps, and records that stream with `MediaRecorder`. An interactive `.pvo` contains one of these recordings per scene. This is the quality and timing boundary; changing the player cannot restore detail already lost in the file.

## Measured behavior

- Before the October 2026 quality change, a new project defaulted to 720p. The export quality selector changed canvas dimensions, but the recorder received no bitrate target. Camera acquisition requested only the facing direction, leaving source resolution to the browser. A controlled Chrome camera test returned 640 × 480 at 20 fps; exporting that recording at 1080p only enlarged those pixels.
- Two recent local `.pvo` exports of the same 8-second, 1080 × 1920, 24 fps HEVC HLG upload contained WebKit VP9 at 720 × 1280 and 1080 × 1920. Both were approximately 9.9 Mb/s video and 8.6 seconds long. Raising the selected resolution did not recover source detail or correct the duration.
- A matched-frame WebKit test showed a colour shift in VP9 WebM output that did not occur in WebKit H.264 MP4 output. On a generated 2-second SDR chart and moving clip, the revised MP4 path retained the measured colour patches and first frame but still encoded about 2.54–2.60 seconds. Chrome WebM encoded about 2.0 seconds. The exact uploaded 8-second MOV still encoded about 8.72 seconds in WebKit. A source playback stall during the real-time render causes the recorder clock to advance while source time does not.
- A local FFmpeg H.264 encode of the generated SDR clip produced about 2.02 seconds at 720p and 1080p. This demonstrates deterministic timing for that fixture. It did not validate HDR tone mapping: the original standard FFmpeg build lacked `zscale`/libplacebo, so HDR requires a build with those filters and a tested HLG-to-SDR conversion.
- With a `zscale`-capable FFmpeg build, the local server renderer produced an 8.000-second, 1080 × 1920 H.264/AAC MP4 from the same original HLG upload that WebKit stretched to about 8.72 seconds. The local server result has a nonblank opening frame. Matched-frame checks against WebKit playback guided the HLG-to-SDR colour adjustment: average RGB error in a low-light frame fell from about 23 to 4 levels out of 255. A bright, saturated synthetic HDR frame improved too, but still showed a visible colour gap; correct timing does not by itself prove full appearance parity.

Run `node scripts/diagnostics/export-quality.mjs` against Vite on port 5173 to repeat the browser comparison. Its passing assertions cover frame content, colour, codec, resolution, motion, and keyframe ratio; it reports duration drift separately because that defect remains open.

## Immediate changes

New projects default to 1080p; 720p remains available for faster, smaller exports, and 4K uses a 2160-pixel short edge. Camera acquisition requests native HD without imposing the project crop on the camera sensor, and recording bitrate follows the actual camera track. Browser export requests 6 Mb/s at 720p, 12 Mb/s at 1080p, or 35 Mb/s at 4K with capability fallback. WebKit prefers H.264 MP4 because its VP9 path shifts colour; Chrome prefers WebM because its MP4 path dropped frames in the diagnostic. These changes improve the input and encoded image, but real-time browser timing defects remain.

## Server rendering path

A server renderer decodes **original** uploaded clips and produces frames on the authored timeline, then encodes with FFmpeg at a deliberate quality, frame rate, and colour transform. Re-encoding a degraded browser export cannot restore source detail. The local beta now exposes private render jobs through `scripts/dev/server.mjs` and uses FFmpeg for eligible flat videos and PVO scene media. The selected 720p, 1080p, or 4K setting determines the output frame size. Visible text overlays and selected soundtrack synthesis continue through the browser renderer until the server can reproduce them faithfully. The export UI names the path used. Four-K processing costs substantially more memory and time; the remote render service still caps results at 200 MiB and publication uploads at 50 MiB.

The Cloudflare Worker now has an owner-scoped render-job contract, private temporary R2 source/result storage and a Queue-to-Container path. The current Wrangler deployment configuration intentionally leaves that remote renderer unavailable until a paid [Cloudflare Container](https://developers.cloudflare.com/containers/) and Queue are provisioned, the D1 migration is applied, and the FFmpeg image is built and checked. See [server rendering](server-rendering.md) for the contract and rollout. A Worker isolate has a 128 MiB memory limit, so FFmpeg runs in the Container. [Container limits](https://developers.cloudflare.com/containers/platform/limits/) and [Worker upload limits](https://developers.cloudflare.com/workers/platform/limits/) determine job sizing and multipart uploads.

The editor uploads original media only after Export is chosen, reports upload/render/download stages, allows cancellation, and deletes the private job after receiving its MP4. It packages server-rendered scene media into `.pvo` locally, keeping components interactive. Publishing remains a separate explicit Create link action.

Production acceptance requires source-to-output frame comparisons for uploaded SDR/HDR and camera-recorded clips; output duration within one frame of the authored duration for ordinary clips; no blank first frame; audio and text parity; playable flat and `.pvo` results across supported browsers; and bounded upload, cancellation, and cleanup behavior. A container built with HDR-aware FFmpeg filters must prove its HLG-to-SDR result against the browser preview before claiming HDR fidelity.
