# Restyle connected Containers — Roadmap 2C

[Roadmap 2](restyle-cloud-agent-roadmaps/02-research-and-connections.md#2c-let-generated-services-use-the-connection) · [Account connections](restyle-account-connections.md) · [Progress](restyle-cloud-agent-progress.md)

## In plain language

2B gives Restyle a private connection to an outside account. 2C lets a published Container ask Restyle to use a specific approved action on that account. The creator can see and approve what the Container will access. The code never receives the account key.

A Container asks for an action by name. Restyle checks its owner, published version, approved account and operation before making the call. Restyle returns only checked data. Normal Try and independent tests use saved example replies and cannot perform real provider actions.

Before a real write, Restyle saves what it intends to do. If the provider's reply is lost, the saved action becomes “needs checking.” Checking an existing action cannot silently send it again. Operations requiring callbacks, background polling or prolonged waiting remain unavailable until Roadmap 3.

## Implementation plan — 8 October 2026

2C.01–03 and 2C.05–07 are checked after local acceptance. 2C.04 and the final deployed-backend gate remain unchecked. Reuse existing saved agreements, release approval, per-service records, account credentials and pinned Node execution. Keep the network-disabled Node guest/image unchanged: a bounded JSON request/result continuation lets trusted host code perform the external call between isolated executions. Generated JavaScript can transform data and choose agreed requests; it cannot control credentials, HTTP headers or provider authority.

- **2C.01:** an agreement can declare named account bindings, permitted service operations and exact adapter descriptions. Creator approval is tied to the checked release. Enforce owner, current release, binding and account status at invocation; keep private account identifiers out of component exports.
- **2C.02:** generated adapters describe bounded inputs, an installed provider's allowed destination/method/path, response projection/schema, permission and synchronous completion. Validate and digest that description before registration. Documentation supports the proposal; it never grants access. A new authentication method requires reviewed trusted platform code.
- **2C.03:** generated code returns a named request; the host validates it, executes the approved adapter outside the guest and supplies only checked results to the next execution. Test replies and expected results remain outside generated source. An arbitrary URL or returned header cannot become a credential target.
- **2C.04:** independent validation and normal Try use saved bounded request/reply examples with exact input matching. A separate isolated acceptance uses a creator-supplied real GitHub read-only token through a private form and a configured hosted Node service. No provider writes are needed for real-account proof; controlled provider tests exercise writes and faults.
- **2C.05/06:** persist service invocation and external request identities before dispatch. Completed results replay without repeating effects. Unknown writes remain durable and use only the installed provider's inspection mechanism; absent evidence never authorizes resending. Account revocation, service changes, restart and cleanup must retain honest outcomes.
- **2C.07:** reject adapters requesting asynchronous completion, callbacks, schedules or repeated polling. Do not add another background runner in this milestone.

## Current contract and limits

- A saved agreement has up to four named connection bindings. Each binds an owned connection reference, exact adapter, allowed service operations and independent input/reply examples. AI proposals must cite documented evidence from a completed page read in the same saved task and current account metadata. Manual edits use the same installed request policy, input/result validation, independent expected-request tests and release approval; editing code does not grant access.
- `execute(invocation)` returns `{result,state}` or one `{request:{connection,input}}`. The trusted host starts fresh Node execution with checked `connectionResults`; generated source never receives the agreement, private connection ID, token, headers, test expectations or authority. A viewer invocation admits up to four outside requests, 8 KiB input and 16 KiB projected result each, under the existing operation deadline. This is not a model iteration limit.
- The installed GitHub policy supports fixed repository metadata, issue/label/milestone reads and explicitly granted issue creation. Recipes select permitted paths and bounded fields, not arbitrary URLs, authentication or headers. Unknown authentication, destinations, methods and asynchronous completion fail closed. A new provider requires a reviewed trusted authentication/request policy; this example does not define future creator requests.
- The optional issue-creation grant is an explicit Restyle permission. Read probes validate account/repository access; they do not certify that GitHub will allow a later write. The provider enforces its token permissions at the actual call. Normal Try and independent tests only receive exact saved example replies, and tests also require the expected requests so a canned answer cannot skip an integration.
- Approval belongs to the exact checked release. Publishing a new version needs its own review. Revocation cancels active continuation and blocks later requests; a slow approval cannot restore a newer revocation. Pausing stops calls. Failed reads can be retried or discarded without an uncertain-write record.
- Before any possible write, both the Container and account owner save its identity. The owner receipt includes the bounded request and checked result, never credentials. It reserves result space before dispatch. Unknown outcomes survive restart and keep the Container’s saved action pending. Different actions and version changes cannot bypass it. Deletion is blocked while such a write is unresolved, with pause and revocation available. The creator can use **Records and usage → Resume saved action** to inspect it and continue remaining approved steps. Disconnect may require reconnection before inspection.
- GitHub issue creation has no assumed idempotency guarantee. The trusted adapter appends a unique request marker and performs at most one bounded read of the latest twenty issues created by the connected account when checking a lost reply. Only one exact author/title/body/marker match confirms a result. Missing, edited, older or ambiguous matches stay “needs checking”; they never cause a new POST. There is no automatic poller or assertion that an unobserved write failed. Roadmap 3 owns extended reconciliation; Roadmap 2D owns manual alternatives.
- Account write receipts are bounded to 2,048 entries and 16 MiB including reserved result space; full storage rejects new writes before dispatch. Completed receipts remain while the Container can replay actions. Deleting a resolved Container removes its approvals/attempts and asks the account owner to remove completed receipts. A failed cleanup reply is visible and retrying the same delete repeats this idempotent cleanup. It never discards an unknown write. Inactive expired versions lose approval with their existing test cleanup.
- Each request continuation can add a fresh Node start and its compute charge; account reads themselves also consume provider quota. The existing Node usage view counts those starts. No always-running VM or new background agent is introduced. Static beta UI, configured account/hosting APIs, isolated acceptance resources and production deployment remain separate.
