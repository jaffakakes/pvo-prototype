# Cloudflare product hosting and publishing

The product deploys from `dist/` through [wrangler.jsonc](../../wrangler.jsonc) and [server/index.js](../../server/index.js). The editor remains at `/editor/`; `/` opens its responsive home. Public [About](../../public/about.html), [Privacy](../../public/privacy.html) and [Terms](../../public/terms.html) pages are copied to the product root. The separate PVO documentation and demo are excluded. Static assets are served directly; API/media requests and published-player templates go through explicit Worker routes. A missing `/player/{id}` asset falls through to the Worker and is resolved from D1, without a general SPA fallback.

Recording and editing are available without an account. Every video and PVO export, download and Create link action requires a Restyle account. The editor offers Google sign-in or Clerk-managed email and password sign-in and retains the project and export settings while sign-in completes. Google identity uses `openid profile`; it does not provide Google Drive or ChatGPT access. `GET /api/auth/session` reports Google and Clerk availability, the public Clerk publishable key, the current user, and whether that user can connect or has connected email sign-in, without creating a session. `GET /api/publishing` returns `{available, hasSession, maxBytes}`; `hasSession` reflects the verified Restyle account. Publishing availability requires `PUBLISHING_ENABLED=true`, private R2 and D1 bindings, an exact HTTPS `PUBLIC_ORIGIN` matching the request, and `SESSION_SECRET`. Google availability separately requires its OAuth client ID and secret. Clerk availability requires a configured Clerk issuer and publishable key.

## Live beta release notifications

`server/worker.js` exports the request handler and the SQLite-backed `ReleaseChannel` Durable Object. The `RELEASES` binding coordinates the beta channel through hibernating WebSockets at `/api/releases/connect`. Each connection receives the persisted release ID; successful announcements broadcast to existing connections. The editor reconnects with backoff after disconnection and when returning online or visible. There is no periodic release check or polling fallback. Browser-managed service-worker checks on navigation still apply.

`npm run deploy` builds the application, then runs `scripts/build/deploy.mjs`. The script provisions an announcement secret through Wrangler's additive `--secrets-file`, deploys, waits for Cloudflare's asset manifest to serve the expected `/editor/release.json`, requires hosted editing, frame-inspection and transcription capabilities from `/api/assistant/status`, exercises one bounded `/api/assistant/turn`, and only then calls `/api/releases/announce`. Release and announcement propagation use bounded retries; authorization failures still fail immediately. The endpoint requires the secret and rejects revisions that do not match deployed assets. The generated secret remains in ignored `.wrangler/release-secrets.json`; CI can supply `RELEASE_NOTIFY_TOKEN`. Never place it in browser code. Use this deployment command rather than a dashboard-only upload so connected clients receive the release event. A failed assistant preflight or announcement makes the command fail even if deployment succeeded. The preflight leaves the uploaded assets in place but does not broadcast the release; rerunning the deployment command safely verifies and re-announces it.

The release ID comes from the existing service-worker content hash. The editor checks for a worker update on a valid release event, downloads it, and retains the existing **New beta release** / **Update** flow. It saves the project before activation and does not interrupt recording. Sleeping or disconnected editors receive the latest release when reconnecting. The native-assistant cutover intentionally has no adapter for the retired `/api/assistant` route. A tab still running the pre-cutover editor can therefore receive an assistant failure until its user accepts **New beta release**; retained static assets do not retain removed server routes.

The local beta server uses `scripts/dev/releases.mjs` to provide the same protocol. When publishing staged output locally, copy assets first, HTML and `sw.js` next, and `editor/release.json` last; the file watcher broadcasts that final revision. Retain old hashed assets for open clients and back up generated output before replacement. Restart a running local server once when introducing the WebSocket route; this does not reload editor tabs.

`node --test tests/release-channel.test.mjs` checks authorization, deployed-asset validation, fan-out, deduplication, and persisted replay after a runtime restart. `npm run check:browser -- editor pwa` checks push delivery without polling, reconnect catch-up, explicit activation, recording protection, saved footage, offline startup, and storage-failure protection.

## Resources and launch configuration

The configured Worker uses the private R2 Standard bucket `pvo-publications-media` and D1 database `pvo-publications-google`, bound as `MEDIA` and `DB`. The resources are provisioned in the Worker's account and recorded in Wrangler. Keep public bucket access through `r2.dev` disabled:

```jsonc
"r2_buckets": [
  { "binding": "MEDIA", "bucket_name": "pvo-publications-media" }
],
"d1_databases": [
  {
    "binding": "DB",
    "database_name": "pvo-publications-google",
    "database_id": "46ed24c3-1bc3-487a-95cf-7b6b58c1db88",
    "migrations_dir": "migrations"
  }
]
```

Apply the checked-in D1 migrations with `npx wrangler d1 migrations apply DB --remote` before enabling sign-in or uploads. In particular, apply [migration 0004](../../migrations/0004_clerk_identities.sql) before deploying a Worker whose signed-in session route queries `managed_identities`; otherwise account checks fail. Migration 0004 has been applied to the production `pvo-publications-google` D1 database. The [initial schema](../../migrations/0001_publishing.sql) stores users, Google provider identities, hashed account sessions, publications and upload attempts; migration 0004 adds explicit Clerk mappings to the same app users. Resource provisioning and remote schema application are deployment setup, not actions performed by a build or the tests.

| Store | Data |
| --- | --- |
| Cloudflare D1 `users` | Restyle user ID, display label, creation time. Google supplies a name; email accounts start with the generic label “Creator”. |
| D1 `provider_identities` | Google account subject mapped to one Restyle user. |
| D1 `managed_identities` | Clerk issuer and user subject mapped to one Restyle user; no email or password. |
| D1 `sessions` | Hash of a random Restyle session token, user ID and expiry. The raw token stays in an HttpOnly cookie. |
| D1 publishing tables | Publication metadata, ownership, upload attempts and quotas. |
| Private Cloudflare R2 | Bytes of published video/PVO exports. |
| Browser IndexedDB | Editable draft projects and source media on that device. |
| Clerk | Email identifiers, passwords, verification, password reset and its own session records. |

The two sign-in methods do not merge accounts by matching a name or email address. Existing Google users connect email from their signed-in account; the editor opens a new Google sign-in, then shows the exact Clerk email and requires explicit confirmation. `POST /api/auth/clerk/link` requires a Google-issued Restyle session created within the past five minutes, a valid Clerk session token, and an `expectedUserId` matching the live cookie owner before it adds a `managed_identities` row for that same Restyle user. A Clerk identity already mapped to another Restyle user is rejected. This preserves the ownership of previously published links. Google `prompt=select_account` confirms which Google account is selected; it does not guarantee that Google asks for a password again.

Create a Google Cloud OAuth **Web application** client for the deployment. Register exactly `https://getrestyle.app/api/auth/google/callback` as an authorized redirect URI; set `PUBLIC_ORIGIN=https://getrestyle.app` without a path. Request only `openid profile`. The Worker starts the authorization-code flow with PKCE, state and nonce, exchanges the code server-side, and verifies the Google ID token before linking its stable `sub` to a Restyle user. See [Google's web-server OAuth guide](https://developers.google.com/identity/protocols/oauth2/web-server) and [OpenID Connect guide](https://developers.google.com/identity/openid-connect/openid-connect).

Store `SESSION_SECRET`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` as Worker secrets with `npx wrangler secret put <NAME>` for each name. Generate `SESSION_SECRET` with at least 32 bytes of entropy. Never place the client secret or session secret in Vite variables, the repository, a static ZIP or a chat message. `GET /api/auth/session` reports `available: true` only when these credentials, D1 and the exact `PUBLIC_ORIGIN` are configured. Set `PUBLISHING_ENABLED=true` and the private `MEDIA` binding separately for link creation. Account availability does not depend on the publishing switch or R2.

For Clerk, configure `CLERK_ISSUER` as the production instance's exact HTTPS Frontend API origin and `CLERK_PUBLISHABLE_KEY` as its public key. Both must belong to the same Clerk instance; never use a development instance in production. The Worker fetches that issuer's `/.well-known/jwks.json` and accepts only recently issued RS256 session tokens with that issuer, an authorized party equal to `PUBLIC_ORIGIN`, no explicit non-active session status, and a Clerk user and session ID. Clerk may omit the status claim for an active personal-account session; a `pending` or other non-active status is rejected. `GET /api/auth/session` reports `clerkAvailable` and `clerkPublishableKey`; the latter is public by design. Clerk passwords and Clerk secret keys are neither sent to nor stored by the Worker. See [Clerk session tokens](https://clerk.com/docs/guides/sessions/session-tokens) and [manual JWT verification](https://clerk.com/docs/guides/sessions/manual-jwt-verification).

The owned `getrestyle.app` Cloudflare zone is active and its Search Console **Domain property** has been verified with Google's DNS TXT record. Keep that TXT record to retain ownership verification. `getrestyle.app` is in Google Auth Platform Branding's authorized domains. After deployment, verify that the Worker serves the approved [homepage](https://getrestyle.app/about.html), [privacy policy](https://getrestyle.app/privacy.html) and [terms](https://getrestyle.app/terms.html) over HTTPS. These exact URLs are set in Branding, and the homepage links both policy pages. Cloudflare Email Routing forwards `support@getrestyle.app` to the verified private contact inbox. The former `workers.dev` address may continue to serve old public viewing links, but the new OAuth callback and public brand use `getrestyle.app`. See [Google's domain verification steps](https://support.google.com/cloud/answer/13804266?hl=en), [OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies) and [Branding requirements](https://support.google.com/cloud/answer/13464321?hl=en).

`GET /api/auth/google/start` opens Google sign-in; `GET /api/auth/google/callback` completes it. `POST /api/auth/clerk/exchange` accepts a short-lived Clerk session token in the `Authorization: Bearer` header and creates or reuses the mapped Restyle account. `POST /api/auth/clerk/link` performs the explicit account connection described above, with JSON `{expectedUserId}`. Both Clerk routes require the exact editor Origin. `POST /api/auth/logout` ends the current Restyle session. The server signs an HttpOnly, Secure, SameSite=Lax `__Host-pvo-session` cookie with the authentication method and issue time and stores only the hash of its random token in D1. Google-derived sessions last seven days; Clerk-derived sessions last fifteen minutes and the editor can re-exchange an active Clerk token when they expire. A revoked Clerk session can leave its last Restyle cookie usable for at most fifteen minutes. The temporary Google OAuth-state cookie lasts ten minutes. Google authorization tokens and Clerk session tokens are not retained. Publication writes require the exact configured Origin and a verified account session. Signing out or cookie expiry does not delete published links.

## Stored exports and limits

`POST /api/publications` reserves storage in one D1 statement with an account-scoped idempotency key. Defaults are 50 MiB per export, 500 MiB reserved/stored per account, 5 GiB total, and 20 newly created links per account per rolling day. Server configuration may reduce these limits; the individual upload maximum never exceeds 50 MiB. Pending and deleting records count toward quota until their storage is removed. A new session for the same Google account does not reset its quota.

`PUT /api/publications/{id}/content` holds an upload lease, writes a new random object key, and enforces the exact reserved size while streaming through a `FixedLengthStream`. Both sides of the stream settle before failed storage is cleaned up. Verification reads bounded metadata from R2: exported MP4/WebM containers, or a PVO header/manifest/asset index of at most 256 KiB and 512 assets. Container inspection is not codec transcoding or full video decoding. PVO metadata validation uses the SDK's public `inspectPvoProject` API; media is never copied into Worker memory. Existing local PVO compatibility and its larger format limits are unchanged.

A conditional D1 write marks the immutable object ready. A repeated completed request returns the same publication; it never replaces its bytes. Concurrent uploads receive a retryable conflict. A failed upload keeps its pending reservation for retry, and every retry gets a fresh object key. A commit whose response is lost is reconciled before deleting any object.

Account-scoped listing returns ready links only. Deletion makes new viewer/media requests unavailable immediately, then removes stored objects and releases quota. An active upload is allowed to settle or expire before its attempt is cleaned up. The hourly scheduled handler expires account sessions and abandoned reservations, retries deletion and scans old unreferenced R2 objects with a persisted cursor. Keep the checked-in cron trigger enabled when publishing is enabled. Cleanup for a missing binding is a no-op for that resource.

`/media/{id}` streams only ready publications, including byte-range responses for native video seeking. Page and media responses are not publicly cached, so new requests recheck removal. Anyone possessing an unlisted link can watch or forward it. Deletion cannot revoke bytes someone already downloaded. PVO playback still downloads the full package before it starts; moving files to R2 does not add adaptive streaming. Published exports are not editable cloud backups.

## Verification and rollout

Run `node --test tests/publishing-server*.test.mjs tests/editor-account-auth.test.mjs` for signed Google and Clerk account sessions, explicit account linking, origin checks, bounded SDK inspection, and integration tests using real local Miniflare D1/R2/Worker execution. `node --test tests/local-google-auth.test.mjs` checks the HTTP loopback Google sign-in adapter. Tests use isolated local storage and a test origin, not remote identity or publishing resources. `npm run check` also discovers these tests. The shared SDK suite checks legacy MP4/MOV and current PVO compatibility.

Run `npm run build`, then a Wrangler dry run, before deploying. A static dashboard ZIP cannot provide the auth or publishing APIs. After configuring resources, secrets, the exact Google callback and the Clerk instance, verify both sign-in methods, sign-out, account linking and export gating against the deployed hostname. Verify both video/PVO uploads, a viewer in a separate browser without sign-in, seeking, idempotent retry, account isolation and deletion. Confirm a linked Google and Clerk identity can manage the same links after fresh sign-in, while a different account cannot. Reading auth/publishing availability must create no account or session; the Google callback and Clerk exchange create one only after successful verification. Local tests do not establish that hosted Google or Clerk credentials, public domain verification, R2/D1 bindings or the deployed session configuration work.

R2 storage/operations, D1 and dynamic Worker requests have separate allowances. Static files bypass Worker execution where possible. Monitor usage and retain quotas; this is bounded hosting, not unlimited free video storage. See [Worker limits](https://developers.cloudflare.com/workers/platform/limits/) and [R2 bindings](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).
